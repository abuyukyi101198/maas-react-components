# Abstract

MAAS UI exposes a view-level search bar for multiple data entities with exclusive table-view pages, most notable example being `machines`. The current implementation of this search bar (and the auxiliary filter dropdown available in a subset of searchable views) has rigid UX with no clear support for constructing complex queries. This specification proposes an extendable DSL and an accompanying UI component with suggestion and grammar support for a more capable query engine in MAAS UI.

# Rationale

As discussed previously in [MA241 - Search and Filter in MAAS UI](https://docs.google.com/document/d/1F-0GEyaprXJkiNsRfyJW0nWbWYZ7vLW0pdL79dg9zGQ/edit?tab=t.0#heading=h.a291qhvyhsw3), the current design for MAAS UI’s search and filter functionality is burdened by two separate components with no UX guidance. The filter dropdown exposes predetermined/prefetched filter options for the table in-view, and inserts the appropriate filter syntax for the selected filter into the search bar.

The search bar component is the main query handler in MAAS UI, and can be modified through filter selection and manual inputs. The availability of the search bar is inconsistent across views, as search as an API capability varies across data entities between API v2 and v3.

The current configuration presents a not-keyboard-friendly query interface with no suggestion engine or logical operators to compose complex queries. The filter dropdown is populated with server-side data for corresponding search fields, and very quickly overflows the page with no internal search option provided. The existing search syntax itself is dissimilar to common query languages, and consequently unintuitive with no autocomplete or suggestion mechanism. Overall, the current configuration forces the user to either sift through the available filters using multiple input methods (keyboard, scroll, click), or know the exact syntax and item name for manual querying.

As API v3 is currently underway, and the future introduction of deployment profiles and instance types will require complex querying capabilities, there is an opportunity to rework the existing query structure for MAAS for the next major 4.0 release.

# Specification

The specification consists of two main parts: the DSL and the component. Incorporating the feedback collected in [MA241 - Search and Filter in MAAS UI](https://docs.google.com/document/d/1F-0GEyaprXJkiNsRfyJW0nWbWYZ7vLW0pdL79dg9zGQ/edit?tab=t.0#heading=h.a291qhvyhsw3), the proposed implementation outlines a strict grammar expanded upon the initial demonstration by [Alessandro Marcolini](mailto:alessandro.marcolini@canonical.com), alongside a prototype-verified revamp of the initial IDE style unified input field designed in [MAAS Prototyping](https://www.figma.com/design/ag3zdHQKoZ4zSzuPwF7Cw0/MAAS-Prototyping?node-id=11-54&t=xZkE6Qr8viZ91QtO-4).

### **Query DSL Grammar**

Following [Alessandro Marcolini](mailto:alessandro.marcolini@canonical.com)’s EBNF-based grammar demonstration, this spec outlines an extendable grammar that allows for client-side suggestions and easy parsing to database queries.

#### **Operator Syntax**

The main difference between this grammar proposal and the existing search syntax found in MAAS UI is the introduction of explicit operators. Binary operators are proposed only as logical chain-builders (`AND`, `OR`), and allow the construction of more complex queries. Unary operators proposed are negation (`NOT`), string matching (`STARTS WITH`, `CONTAINS`, `ENDS WITH`), and numeric limits (`AT LEAST`, `AT MOST`, `ABOVE`, `BELOW`). Operators must be uppercase.

Logical precedence is `NOT`, then `AND`, then `OR`; parentheses override this order.

#### **String Syntax**

A comment on [MA241 - Search and Filter in MAAS UI](https://docs.google.com/document/d/1F-0GEyaprXJkiNsRfyJW0nWbWYZ7vLW0pdL79dg9zGQ/edit?tab=t.0#heading=h.uaf9aoxb8221) was the possibility of grammar tokens appearing in fuzzy match strings (e.g. a tag named `NOT-READY`). This specification addresses that issue by expecting encasing double-quotes for match strings. Therefore, the query below:

```
STARTS WITH "mgmnt-" AND CONTAINS "001"
```

would query items of the in-view table that have names starting with `mgmnt-` and containing `001` anywhere. String syntax can be used to match the name of the in-view data entity, or as a value for filters.

Without a unary string operator, a quoted string is an exact match. All string comparisons are case-sensitive. Quoted strings support all JSON escapes, including `\"` and `\\` for embedded quotes and backslashes. Characters such as `%`, `_`, and `*` are literal, not wildcards.

#### **Filter Syntax**

Filters follow a simplified but more verbose version of the current `filter:(=value1, =value2, …)` syntax. In addition to introducing internal and external operator support for filters, this syntax also proposes nested filters as a means of suggestion optimization. An outer filter may contain one level of nested filters; grouping parentheses do not count toward this limit. The proposed grammar is as follows:

```
status("Ready")
status(NOT "Ready")
status("Ready" OR "New")
status("Ready") AND pool("default")
fabric(vlan("vlan-1"))
fabric(STARTS WITH "mgmnt-" AND vlan(ENDS WITH "-maas"))
```

This filter syntax removes the redundant syntactic sugar in the current syntax, and allows for nested filtering for deep-match queries checking joined tables.

Filter names must be lowercase. For filters with internal chaining, the entire internal expression must match a data entity item for it to be returned. Separate invocations may match different items. In the example below, the internal chain must match a `machine` connected to the matching VLAN within the matching fabric through its interface path. The VLAN merely existing elsewhere in that fabric is insufficient. The external chain, however, can match separate `fabric` items.

```
// matches machines with at least one fabric matching BOTH conditions
fabric(STARTS WITH "mgmnt-" AND vlan(ENDS WITH "-maas"))

// matches machines with at least one fabric matching EACH condition
fabric(STARTS WITH "mgmnt-") AND fabric(vlan(ENDS WITH "-maas"))
```

Negation outside a collection filter matches when no member satisfies its condition, including when the collection is empty. Negation inside the filter requires an existing member satisfying the negated condition.

For example, `NOT fabric("production")` matches machines with no connection to the production fabric. `fabric(NOT "production")` matches machines connected to at least one other fabric, even if they are also connected to production. Unknown scalar values satisfy neither a comparison nor its negation.

#### **Unit Syntax**

Introduced specifically for numeric fields, this specification proposes the introduction of field-specific units to use for exact matches, or the aforementioned numeric limit unary operators. Unitless values use the field’s default base unit. Numbers follow `[+-]?[0-9]+(\.[0-9]+)?`, with optional whitespace before a unit: `8GiB` and `8 GiB` are equivalent.

For the following queries on the `machine` table, `disk` selects individual disks and `size` denotes their capacity in bytes:

```
disk(size(8GiB))
disk(size(8GiB OR 12GiB))
disk(size(8GiB AND 12GiB))
disk(size(AT LEAST 8GiB AND AT MOST 12GiB))
disk(size(AT LEAST 8GiB)) AND disk(size(AT MOST 12GiB))
```

would yield the following results:

- `machine` with a disk of  *exactly* `8GiB`
- `machine` with a disk of *exactly* `8GiB` or *exactly* `12GiB`
- `machine` with a single disk of *exactly* `8GiB` and *exactly* `12GiB` (this is an impossible query that would return `[]`)
- `machine` with a disk in the range of `8GiB` to `12GiB` (inclusive)
- `machine` with a disk of *at least* `8GiB`, and a disk of *at most* `12GiB`, which may be different disks; for example a machine with `16GiB` and `4GiB` disks matches this query, but not the previous one

#### **Grouping Syntax**

With logical operators introduced, operation ordering becomes important. This proposal also introduces parentheses as the conventional method of grouping in- and out- filter chains. The following examples override the default `AND` prioritization in logical operations:

```
(pool("default") OR zone("zone-1")) AND owner("user-1")
architecture((STARTS WITH "amd64" OR STARTS WITH "arm64") AND CONTAINS "generic")
```

### **Context-Aware Suggestions**

A strict and parseable grammar allows for easily trackable context for suggestion insertions and autocomplete. As the user constructs or edits a query, the position of their input can be traced to an enclosing context using the out-of-the-box grammar parsing combined with smart trimming of incomplete tokens.

Context can be split into 2 broad levels: base and filter. Base-level context suggests filters for the in-view data entity, while filter-level context narrows suggestions to the field corresponding to the active filter. Base-level context can be deduced solely from the in-view data entity type, and can be handled by the client-side. Filter-level can be used to suggest value matching actual values fetched from the server-side, or nested filters in the client as done with base-level.

Since the grammar is strictly defined on the client-side, operators can be suggested by rule parsing solely in the client.

Below is an example of state/suggestion pairings for `machine`, where `|` indicates caret (active context) position. Lists are illustrative rather than exhaustive, and do not prescribe presentation order.

```
| -> [NOT, CONTAINS, STARTS WITH, ENDS WITH, status(), pool(), zone(), ...] (client)
NOT | -> [status(), pool(), zone(), ...] (client)
status(|) -> [NOT, CONTAINS, "Ready", "New", "Deployed", ...] (client & server)
status("Ready" |) -> [AND, OR] (client)
status("Ready" OR |) -> [NOT, "Ready", "New", "Deployed", ...] (client & server)
fabric(|) -> [vlan(), "fabric-0", "fabric-1", ...] (client & server)
```

Base and nested filters are suggested by the client using type lookup, alongside logical operators, while value suggestions are fetched from the server-side. Autocomplete works with the same principle, used to reduce the suggestions to those matching the incomplete token. For example:

```
sta| -> [status()] (client)
NO| -> [NOT] (client)
status("Rea|") -> ["Ready"] (server)
```

These examples reduce the suggestion list to only the items matching the token within the active context.

Filter and operator autocomplete uses case-insensitive prefix matching, while inserted tokens match their type’s capitalization: lowercase for filters, uppercase for operators. Value lookup is scoped by entity type, nested filter context, partial token, and permissions, independently of other predicates in the query.

Trimming incomplete inputs is for suggestion analysis only. Execution requires a complete and valid query, never a shortened prefix.

### **Permission Gating**

Context-aware suggestions introduce a risk of exposing information to unauthorized users through the search, and must respond in accordance with fine-grain permissions. Users will be restricted to receiving suggestions only for the values they are permitted to view, while administrators can receive suggestions for all values. Type-aware filter suggestions do not need to be subject to permissions since they are client-side rules dependent on the data-entity type.

If an unpermitted query is manually typed, the response will act as the permission gate, returning only items matching the query *and* the user permissions.

## User Stories

### **\[1\] As a MAAS administrator, I want to identify ready machines in suitable pools or zones, so that I can select candidates for deployment.**

#### **Acceptance criteria:**

* The administrator can combine readiness with pool and zone conditions in one query.
* Grouping allows alternative locations without relaxing the readiness requirement.
* Conditions can be negated to exclude unsuitable candidates.
* Context-aware suggestions help the administrator discover filters and available values while constructing the query.

### **\[2\] As a MAAS administrator, I want to find machines with a disk meeting a capacity requirement and a VLAN on the required fabric, so that I can select hardware with the appropriate storage and connectivity.**

#### **Acceptance criteria:**

* Disk capacity can be matched using exact values or numeric limits with units.
* Single disk enforcing and multiple disk enforcing rules can be distinguished, and conditions can be relaxed to match machines with multiple disk configurations.
* The machine must be connected to the matching VLAN within the fabric satisfying the fabric condition.
* Returned machines must satisfy both the storage and connectivity requirements.

### **\[3\] As a MAAS operator, I want to find machines of a particular architecture with deployment-failure statuses, so that I can investigate whether a deployment image is associated with those failures.**

#### **Acceptance criteria:**

* An exact architecture match can be broadened to an architecture family using a string operator.
* Architecture and deployment-failure status conditions can be combined in one query.
* Multiple failure statuses can be included without relaxing the architecture requirement.

# Scenarios

### **Scenario 1: Filter with Suggestions**

1. The user wants to find deployed machines in the default zone.
2. The user focuses on the unified search input above the machine table.
3. The user begins typing `sta` and receives live suggestions for filters.
4. The user selects `status(` from the list using the keyboard, and automatically gets the closing parenthesis, while still writing within.
5. The user types `"`, and automatically gets the closing quote, while still writing within.
6. The user types `dep`, receives value suggestions like `Deployed`.
7. The user selects `Deployed`, moves outside the filter parentheses then adds a space.
8. The user selects `AND` from the operator suggestions that appear after the space is added.
9. The user executes the same steps for the zone filter.
10. The user hits submit, or `Ctrl+Enter`.
11. Matching machines in the “Deployed” status and “Default” zone are shown.

### **Scenario 2: Group Alternative Deployment Locations**

1. The user wants ready machines in either the default pool or zone-1.
2. The user constructs the status filter for “Ready” using suggestions.
3. The user moves outside the filter, adds `AND`, then opens a group with `(`.
4. Inside the group, the user constructs the pool filter for “default”.
5. The user adds `OR`, then constructs the zone filter for “zone-1”.
6. The user moves outside the group.
7. The user hits submit, or `Ctrl+Enter`.
8. Ready machines matching either location are shown.

### **Scenario 3: Share and Reuse a Complete Query**

1. The user constructs and executes a query.
2. The user selects the complete query in the search input and copies it.
3. The user sends the copied query to another user as text.
4. The recipient copies the query and pastes it into the search input above the same entity table.
5. The input recognizes the complete query, preserving its filters, operators, values, and grouping.
6. The recipient hits submit, or `Ctrl+Enter`.
7. Matching machines are shown according to the recipient’s permissions.

### **Scenario 4: Exclude Items with Negation**

1. The user has constructed a query for ready machines.
2. The user wants to exclude machines in the reserve pool.
3. The user moves outside the status filter and adds a space.
4. The user selects `AND`, then selects `NOT` from the operator suggestions.
5. The user selects the `pool` filter and chooses “reserve” from its value suggestions.
6. The user moves outside the filter.
7. The user hits submit, or `Ctrl+Enter`.
8. Ready machines are shown, excluding those in the reserve pool.

## Implementation

### **API Changes**

API v3 will support query execution and context-aware value suggestions. Adoption starts with `zones`, whose flat data model does not require nested filtering, then extends to other v3 entity listings. API v2 views retain their existing search behavior until migrated to v3.

#### **Query Execution Endpoint**

Each supported entity exposes a read-only search endpoint:

```
POST /MAAS/a/v3/{entity}:search/
Content-Type: application/json
```

The initial endpoint is `/MAAS/a/v3/zones:search/`. Search reuses the entity’s listing behavior and response structure; it does not create or modify resources.

The request body is a JSON object containing:

| Field | Required | Description |
| :---- | :---- | :---- |
| `query` | Yes | The normalized expression AST defined below. |
| Listing controls | No | The entity listing’s pagination, sorting, and grouping parameters, using their existing field names, types, and defaults where supported. |

Listing controls are top-level body fields alongside `query`, not URL query parameters. The client sends the structured representation, not the DSL string, and the server does not parse user-facing DSL text.

The server validates the submitted structure and the filters, operators, value types, and nesting supported by the target entity. Client-side validation does not replace this check. Execution must preserve the matching, grouping, and negation semantics defined above rather than reduce the query to independent flat filters.

Query filtering is integrated with the listing’s existing sorting, pagination, and grouping where supported. Filtering and permissions apply before pagination and grouping; results and totals count each entity once, regardless of how many related items match. The existing listing response structure is retained.

Successful searches return `200 OK` with the entity’s existing listing response, including its pagination and count metadata where supported. The client repeats the applied query in the body of subsequent search requests when changing pages, sorting, or grouping. Clear returns to the entity’s normal unfiltered listing operation within the user’s permissions.

#### **Structured Query Representation**

`query` contains one expression node, without an additional query wrapper. The supported node types are:

| `type` | Required fields | Meaning |
| :---- | :---- | :---- |
| `and`, `or` | `operands`: an array of at least two expression nodes | Logical conjunction or disjunction. |
| `not` | `operand`: one expression node | Negates the enclosed expression. |
| `filter` | `name`: a lowercase filter name; `expression`: one expression node | Evaluates the expression within that filter’s scope. |
| `comparison` | `operator`: a comparison identifier; `value`: a value node | Compares the active field with the supplied value. |

Comparison identifiers are `equal`, `contains`, `startsWith`, `endsWith`, `above`, `below`, `atLeast`, and `atMost`. These identifiers are API values; the DSL continues to use uppercase operator keywords.

Value nodes have the following forms:

| `type` | Required fields | Meaning |
| :---- | :---- | :---- |
| `literal` | `value`: a JSON string | The decoded string value, without DSL quote delimiters. |
| `quantity` | `amount`: a decimal string; `unit`: a unit string or `null` | A numeric quantity; `null` selects the field’s default unit. |

`amount` follows the numeric syntax defined under Unit Syntax and remains a string to preserve precision. `equal` accepts either value type; string operators require `literal`, and numeric operators require `quantity`. The target field must support the supplied comparison and value type.

At base level, string comparisons target the entity name. A bare quoted string becomes an `equal` comparison, not a separate fuzzy-search node. Numeric comparisons occur within filters.

Expression nesting captures precedence, so no grouping nodes are transmitted. The representation also omits `scope` and `quoted` metadata. Filter boundaries and the position of `not` are preserved; separate filter invocations must not be merged. The server validates node shapes and the DSL’s nesting constraints independently of the client.

For example, `disk(size(AT LEAST 8GiB))` is submitted as:

```json
{
  "query": {
    "type": "filter",
    "name": "disk",
    "expression": {
      "type": "filter",
      "name": "size",
      "expression": {
        "type": "comparison",
        "operator": "atLeast",
        "value": {
          "type": "quantity",
          "amount": "8",
          "unit": "GiB"
        }
      }
    }
  }
}
```

**Base-level string operators:** `STARTS WITH "mgmnt-" AND CONTAINS "001"`.

```json
{
  "query": {
    "type": "and",
    "operands": [
      {
        "type": "comparison",
        "operator": "startsWith",
        "value": { "type": "literal", "value": "mgmnt-" }
      },
      {
        "type": "comparison",
        "operator": "contains",
        "value": { "type": "literal", "value": "001" }
      }
    ]
  }
}
```

**Grouped logical operators:** `status("Ready") AND (pool("default") OR zone("zone-1"))`. The nested `or` captures the parentheses without a grouping node.

```json
{
  "query": {
    "type": "and",
    "operands": [
      {
        "type": "filter",
        "name": "status",
        "expression": {
          "type": "comparison",
          "operator": "equal",
          "value": { "type": "literal", "value": "Ready" }
        }
      },
      {
        "type": "or",
        "operands": [
          {
            "type": "filter",
            "name": "pool",
            "expression": {
              "type": "comparison",
              "operator": "equal",
              "value": { "type": "literal", "value": "default" }
            }
          },
          {
            "type": "filter",
            "name": "zone",
            "expression": {
              "type": "comparison",
              "operator": "equal",
              "value": { "type": "literal", "value": "zone-1" }
            }
          }
        ]
      }
    ]
  }
}
```

**Outer negation:** `NOT fabric("production")`. The `not` encloses the filter, requiring no matching fabric.

```json
{
  "query": {
    "type": "not",
    "operand": {
      "type": "filter",
      "name": "fabric",
      "expression": {
        "type": "comparison",
        "operator": "equal",
        "value": { "type": "literal", "value": "production" }
      }
    }
  }
}
```

**Inner negation:** `fabric(NOT "prod")`. The `not` is inside the filter, requiring an existing fabric satisfying the negated comparison.

```json
{
  "query": {
    "type": "filter",
    "name": "fabric",
    "expression": {
      "type": "not",
      "operand": {
        "type": "comparison",
        "operator": "equal",
        "value": { "type": "literal", "value": "prod" }
      }
    }
  }
}
```

#### **Filter Value Suggestion Endpoint**

A shared endpoint serves value suggestions for the searchable v3 entities:

```
GET /MAAS/a/v3/autocomplete/?entity=<entity>&filter=<filter>&q=<partial>&limit=<limit>
```

Query parameters:

| Parameter | Required | Description |
| :---- | :---- | :---- |
| `entity` | Yes | The entity being searched, such as `images` or `machines`. |
| `filter` | Yes | The filter whose values are requested, such as `zone` or `vlan`. |
| `parent` | No | The enclosing filter for a nested lookup, such as `fabric` when requesting `vlan` values. Omitted for root-level filters. |
| `q` | No | The partial value. Omitted or empty input requests initial suggestions. |
| `limit` | Yes | A positive integer specifying the maximum number of values to return. |

Parameter values must be URL-encoded. For example, a machine zone lookup uses:

```
GET /MAAS/a/v3/autocomplete/?entity=machines&filter=zone&q=def&limit=4
```

A nested VLAN lookup uses `entity=machines`, `filter=vlan`, and `parent=fabric`; the rest of the query is not sent.

Lookup uses case-insensitive substring matching and is independent of the other predicates in the query. Only values the requester is permitted to view are eligible. This lookup behavior does not alter the case-sensitive comparisons used during query execution.

Successful lookups return `200 OK` with a JSON object containing matching strings:

```json
{
  "suggestions": [
    "default"
  ]
}
```

The list is bounded by `limit`, without pagination or separate display-label/query-value pairs. A successful lookup with no matches returns `{"suggestions": []}`. Lookup failures must be reported as errors, not empty successful responses, so the UI can distinguish failure from “No matching values”.

Filter names and operators remain client-side suggestions; this operation supplies values only.

#### **Validation and Permissions**

Malformed query structures and unsupported filters, operators, value types, or nesting are rejected with a validation error. Suggestion requests with unsupported entity/filter contexts or invalid parameters are also rejected. Both endpoints use API v3’s error response conventions; query validation errors must identify the offending expression sufficiently for the client to explain the rejection.

A valid value that is absent from the data simply does not match; it is not a validation error, and its predicate must not be silently ignored. Valid but unsatisfiable queries return an empty result.

Authorization applies to the complete query result, including expressions containing `OR` or `NOT`, and to listing totals and value suggestions. Manually entered values receive the same checks as suggested values. Execution failures are reported as errors rather than successful empty listings.

### **Backend Changes**

A shared translator converts the validated normalized AST into SQLAlchemy predicates through the existing `QuerySpec` / `Clause` architecture. It handles logical nodes and comparison operators centrally, while entity-specific filter registries beside the repositories resolve allowed names to scalar fields or relationships and define supported operators, value types, and units. These registries form the backend filter catalogue; arbitrary database columns are not exposed.

Scalar comparisons use parameterized SQLAlchemy expressions. String matching preserves case sensitivity and escapes SQL wildcard characters to retain the DSL’s literal-string semantics. Entity, field, relationship scope, and table aliases are carried in per-query translation context, not mutable global state.

Each collection-filter invocation produces a correlated `EXISTS` predicate. Conditions within one invocation share that scope; separate invocations produce independent predicates. Negation directly outside a collection filter becomes `NOT EXISTS`, while inner negation remains within the relationship predicate. Scalar comparisons and their negations preserve the defined unknown-value semantics. Relationship definitions preserve the required connection to the root entity rather than accumulating shared joins.

Permission resolution remains outside the translator. The listing execution path combines authorization with the translated predicate through `QuerySpec`. Filtering and authorization apply before grouping and pagination, preserving existing sorting behavior and ensuring that results and totals count each root entity once.

### **UI Changes**

The existing search field and filter dropdown will be replaced by a unified query input above the relevant table, with Submit and Clear buttons. Query construction, editing, and submission will support both keyboard and mouse use.

#### **Unified Search Component**

* Filters and operators are rendered as distinct chips using the Vanilla chip pattern. Filter chips use a neutral background; operator chips use the information colour.
* Filter boundaries visually enclose their contents, including nested filters. Grouping parentheses remain visible as text.
* Values remain editable text. Filter names and operators are atomic chips rather than individually editable characters.
* Long queries wrap within the input without introducing line breaks into the query.
* Selecting query content outlines the affected chips. Nested filters retain their individual boundaries.

#### **Grammar Definition**

* Grammar is housed in a `.peggy` file, with its corresponding package `peggy` installed in `devDependencies`.
* Grammar building generates JavaScript and TypeScript files to be imported by the component.
* Grammar build is added as a script, and the script is invoked during the full build of the UI.

#### **API Query Configuration**

* API v3 uses TanStack Query. The normal listing and search endpoint have separate query keys and cached responses. Search is a read operation managed through `useQuery`, even though its request uses POST.
* The search query key includes the entity, submitted normalized AST, and pagination, sorting, and grouping controls. Draft edits do not change this key or initiate requests; submitting a valid query activates the search data source.
* The table conditionally consumes either the normal listing response or the active search response, including its counts and pagination metadata. Search responses do not overwrite the normal listing cache.
* While a search is applied, loading and error states come from that search query. An empty search result remains an empty table, not a fallback to the normal listing. Changing pages or listing controls requests data from the active source.
* Clear switches the table back to the normal listing source on its first page, preserving selected rows. Late search responses must not replace the listing after Clear or the results of a newer applied query.
* Search queries use `gcTime: 30_000`, retaining unused results for only 30 seconds to avoid accumulating query-specific datasets in client RAM. Replaced or cleared search queries must no longer be observed; disabling their requests alone is insufficient to release their cache. Active search results remain available while displayed.
* `staleTime` controls freshness, not cache removal. The short search retention policy does not change the normal listing’s cache configuration.

#### **Query Construction and Editing**

* Selecting a filter inserts its lowercase name and paired parentheses, with the caret inside.
* Typing an opening grouping parenthesis or string quote inserts the corresponding closing character, with the caret between them. Typing the matching closing character immediately before an automatically inserted closer moves past it rather than duplicating it.
* Selecting a value replaces the active partial value, preserving surrounding query content. String values are quoted and escaped, without duplicating existing quotes or filter-closing parentheses.
* After selecting a value, the caret remains inside the filter, following the completed value.
* Selecting an operator inserts its uppercase form with separating whitespace and leaves the caret ready for the next term.
* `Left` and `Right` move through editable values and across atomic chips. Moving the caret or clicking elsewhere in the query updates the suggestion context.
* `Backspace` at a filter’s inner opening boundary or immediately after its closing boundary first highlights the whole filter. A second `Backspace` removes it, including its contents. The same two-step behavior applies immediately after an operator chip.
* Moving the caret or clicking elsewhere cancels the deletion highlight.
* Standard Undo/Redo covers text edits and structural edits, including suggestion insertion, automatic pairing, chip deletion, paste, and clearing. Each structural edit is undoable as one action.
* Undoing Clear restores the query draft only; Submit is required to apply it again.

#### **Suggestion List**

* Suggestions appear beneath the input and follow the active caret context, including when editing an existing query.
* Each suggestion displays its value and type. Filter and operator suggestions use the same chip styling as the input.
* 4 suggestions are shown initially. If more are available, a “Show more” entry expands the list to a maximum of 15 suggestions. Editing the query or inserting a suggestion returns the list to its initial size.
* The first suggestion is highlighted when the list opens. `Up` and `Down` move the highlight, wrapping at either end. `Enter` inserts the highlighted suggestion. Hovering highlights an item, and clicking inserts it.
* Selecting a filter or operator keeps suggestions available for the next term. Selecting a value dismisses the list.
* Suggestions are withheld where insertion would overwrite an existing filter or operator chip. Immediately after a closing quote or parenthesis, the list stays closed; adding a separating space allows continuation suggestions.
* Clicking outside the input dismisses suggestions without submitting or clearing the query.
* When the caret context changes, values from the previous context are removed immediately. A loading indicator is shown during lookup, alongside applicable local filter/operator suggestions. Late responses for an old context are ignored.
* A successful lookup with no matching values displays “No matching values”, alongside any applicable local suggestions.
* A failed value lookup displays a failure message with Retry. Local filter/operator suggestions remain usable.

#### **Submission and Cancellation**

* The query is parsed as it is edited. Incomplete or invalid queries disable Submit and display a red exclamation-circle error icon within the button. An error tooltip is available on hover or keyboard focus of an accessible error indicator, including while Submit is disabled.
* Empty or whitespace-only input also disables Submit.
* Only complete, valid, non-empty queries can be submitted. Submit or `Ctrl+Enter` applies the query to the table; `Cmd+Enter` provides the equivalent shortcut on Mac platforms.
* The submission shortcut does nothing while Submit is disabled.
* Editing, selecting suggestions, or moving the caret does not change the applied table results.
* If query execution fails, the table results are replaced by an error state.
* Clear empties the input, closes suggestions, clears validation feedback, and resets the table to its unfiltered state within the user’s permissions. Pagination returns to the first page; selected rows are preserved.
* `Esc` dismisses suggestions when they are open; otherwise it performs Clear.
* `Enter` without a modifier selects a highlighted suggestion; it does not submit the query or insert a line break.

#### **Copy and Paste**

* Copying a query produces its DSL text, including the parentheses represented by filter boundaries, rather than chip markup.
* Pasted text replaces the current selection or is inserted at the caret. Recognized valid fragments are rendered as chips immediately; invalid fragments remain editable for correction.
* Pasted queries are validated like manually entered queries and are never submitted automatically.
